// DESIGN · AGENT SYSTEM

A design team of agents that makes every screen usable, consistent and accessible

Seven agents that work like a small design org. One owns the design system so the UI stays consistent. One tests with real users. One designs the flows and screens. One checks accessibility and usability before anything ships. One hands off specs and checks the built UI against them. One measures whether users succeed. An orchestrator keeps design aligned with what Product is solving and what Engineering is building. Copy the setup prompt into Claude. It will interview you about your product and brand and then write the whole system as a folder of agent files.

design system tokens UX research flows & prototypes UX copy accessibility handoff & QA

The goal the system works toward

Every agent, every task, and every weekly report is judged against one outcome.

// north star

Every screen users touch is usable, accessible and consistent, so users complete key tasks on the first try and engineering ships UI fast without building up design debt.

The system doesn't count polished mockups as wins. Success is users completing tasks in the shipped product. Problems and specs come from the Product agent system, and the design system is the shared language the Engineering agents build with.

How the agents work together

The orchestrator sets the week's design priorities. Work moves from foundations (the design system and user research) to designing flows and screens, and then to review, handoff and shipping. Product problems and specs come in from the Product system. Design Quality & UX Metrics measures the shipped experience and sends a scorecard back, so next week's priorities are based on where users actually struggle. Click any agent to jump to its role.

The agents and what each one does

Each agent becomes its own markdown file. The defaults below are best practice. The setup interview adjusts them to your product, platforms, brand, team and tools.

// control

Design Orchestrator

Acts as head of design. Takes in work from Product, decides what gets designed this week and how much finish it needs, runs critiques, and brings you only the decisions that need you.

Does
  • Turns product specs and the scorecard into design briefs: the problem, the users, the constraints, and the definition of done.
  • Matches the level of finish to the risk. Small changes go straight to the design system; new flows go through wireframes, a prototype and a usability test.
  • Runs a weekly critique against your design principles and collects everything that needs your approval into one list.
Asks you
  • Who designs today (nobody, a part-time designer, a team), the current design goals, and who has the final say on UI and brand.
→ agents/design-orchestrator.md
// 01 · foundations

Design System

Owns the tokens and components every screen is built from, so the product looks and behaves like one app rather than four.

Does
  • Defines semantic tokens (color, spacing, type, radius, shadow, motion) in one source of truth that syncs to Figma variables and to code (see the example design-system.md).
  • Maintains about 25 components, each with every state documented (hover, focus, disabled, loading, error, empty), its API and its keyboard behavior.
  • Answers "is there a component for X?" before anyone builds a one-off. It can optionally run as a tool that Engineering agents call.
Asks you
  • Your brand assets, your front-end stack (e.g. React + Tailwind + shadcn/ui), and whether you have a Figma library or Storybook.
→ agents/design-system.md
// 01 · foundations

UX Research

Grounds design decisions in what users actually do, by testing early and cheaply instead of debating in meetings.

Does
  • Writes test plans and task scripts. A round of usability testing with about 5 users catches most problems in a flow.
  • Synthesizes sessions, recordings and feedback into issues ranked by severity, each with direct quotes and how often it occurred.
  • Handles consent forms and anonymizes notes. Recordings and personal data stay in the research tool.
Asks you
  • Your users and key tasks, existing research, where to find participants, and any research tools you use (Maze, Lookback, Dovetail, UserTesting).
→ agents/ux-research.md
// 02 · design

UX & UI Design

Designs flows and screens that solve the problem in the brief, using only parts from the design system.

Does
  • Starts from the user's task and the flow, then low-fidelity wireframes, before any polished screens. It explores 2–3 options before converging.
  • Designs every state (empty, loading, error, partial, success) and every breakpoint, and builds clickable prototypes for testing.
  • Writes the UX copy: sentence case, verb-first buttons, and error messages that say what happened and how to fix it. No "Oops!"
Asks you
  • Your platforms and breakpoints, design principles, brand voice, and any reference products you admire.
→ agents/ux-ui-design.md
// 03 · review & ship

Accessibility & Design Review

Makes sure every design is accessible and usable before it reaches engineering, where fixes cost ten times more.

Does
  • Audits designs against WCAG 2.2 AA: contrast, focus order and visibility, target size, labels, motion, and not relying on color alone.
  • Critiques designs against usability heuristics and your design principles, with each issue ranked blocking or suggestion.
  • For built UI: automated checks (axe-core) plus manual keyboard and screen-reader passes (VoiceOver, NVDA).
Asks you
  • Your accessibility target, whether customers ask for an accessibility conformance report (VPAT), and any known users with accessibility needs.
→ agents/accessibility-review.md
// 03 · review & ship

Design QA & Handoff

Makes sure what ships matches what was designed, without endless back-and-forth with engineering.

Does
  • Writes handoff specs that Engineering agents can build from: the components and tokens to use (never raw hex values), every state, responsive behavior, interactions, final copy and edge cases.
  • Reviews UI pull requests. It blocks on token violations, accessibility regressions and one-off components, and only suggests on spacing and copy.
  • Compares the built UI with the design in light and dark mode, and logs drift as design debt.
Asks you
  • Your code repository and pull-request process, your issue tracker, and whether design review should block merges.
→ agents/design-qa-handoff.md
// measure & learn

Design Quality & UX Metrics

Measures whether design is working for users, and whether the system is holding together, so the next priority is based on evidence.

Does
  • Tracks task success, time on task, and ease ratings (SUS, or a single ease question after each task) on key flows.
  • Tracks design-system adoption: the share of UI built from library components, the number of one-offs and hard-coded values, and open accessibility issues.
  • If you have product analytics or session replay (e.g. PostHog), asks you to connect it read-only to find where users struggle. It writes a weekly design scorecard.
Asks you
  • Your analytics and session-replay tools, the key flows to track, and your current baselines if known.
→ agents/design-metrics.md

// always needs your approval

  • Publishing the design library or changing tokens
  • Adding, changing or removing shared components
  • Designs moving to "ready for engineering"
  • Recruiting or contacting users, and incentives
  • Brand changes and anything that ships to production

// red flags to watch

  • One-off components multiplying: the system is missing a part, or isn't being used
  • Lots of hard-coded hex values and spacing in code: tokens aren't wired into the build
  • Designs approved but never tested: usability problems surface in production
  • Accessibility found only at the end: it isn't part of design review
  • Built UI drifting from the designs: handoff specs are missing states or edge cases
