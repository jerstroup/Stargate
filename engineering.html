// ENGINEERING · AGENT SYSTEM

An engineering team of agents that turns approved specs into safe, shipped software

Seven agents that work like a small, disciplined engineering org. One keeps the repo understandable to agents. One breaks specs into PR-sized tasks. One writes the code and tests. One reviews every pull request for correctness and security. One handles releases and incidents. One measures quality and flow. An orchestrator limits work in progress so humans never drown in agent output. People approve every spec, every merge and every production change. Copy the setup prompt into Claude Code. It will interview you about your codebase and team and then write the whole system as a folder of agent files.

CLAUDE.md & skills MCP planning one task, one PR review in CI release & oncall evals & flow metrics

The goal the system works toward

Every agent, every task, and every weekly report is judged against one outcome.

// north star

Ship working, secure software fast: approved specs become merged, tested, production-ready code, with a person approving every step that can't be undone.

Lines of code and PRs opened don't count as wins. The system tracks how fast an approved spec reaches main, how often agent PRs merge without rework, and how many bugs reach users. Specs arrive from the Product agent system. UI work follows the Design system's components and tokens.

Speed
Spec-to-merge lead time (p50 / p90)
Quality
First-pass merge rate · escaped defects per spec
Health
Eval pass rate · review wait < 24h
Guardrail
0 unapproved prod changes · 0 secrets in agent context

How the agents work together

The orchestrator sets the week's specs and work-in-progress limits. Work moves from planning to building and then to shipping. Approved specs arrive from Product. Evals & Flow Metrics watches every PR, deploy and incident and sends a scorecard back, so next week's limits and prompts are based on what actually happened. Click any agent to jump to its role.

The agents and what each one does

Each agent becomes its own markdown file. The defaults below are best practice. The setup interview adjusts them to your stack, stage, team and tools.

// control

Engineering Orchestrator

Acts as tech lead and flow engineer. Picks which specs ship this week and enforces work-in-progress limits, so agents build only as fast as people can review. Writes the daily status so meetings stay short.

Does
  • Runs an agentic Kanban board: Spec ready → Agent building → Agent self-check → Human review → CI + evals → Canary → Done.
  • Enforces WIP limits: at most 3 PRs per person waiting in review, 1 active branch per agent, and a cap on merges per day. When a limit is hit, new work pauses.
  • Runs the rituals: an async standup (10 minutes), weekly planning, spec review, a prompt and eval review, a demo, and a retro.
  • Sizes the setup to your stage. Before product-market fit it starts with the minimum: context, coder, PR loop and reviewer.
Asks you
  • Team size, stage, cycle length, who reviews code, and this quarter's engineering priorities.
→ agents/engineering-orchestrator.md
// 01 · plan

Repo Context Steward

Keeps the codebase understandable to agents. If an agent can't reproduce a workflow from the repo and CLAUDE.md alone, this agent documents the gap.

Does
  • Writes and maintains CLAUDE.md: architecture, "how we do X", rules that must never break, and commands (see the example CLAUDE.md).
  • Standardizes on one coding agent and commits the shared settings, subagents and skills to the repo. Turns any workflow solved twice into a reusable skill.
  • Adds MCP servers one at a time, only when a task needs them: database (read-only, staging only), logs, issue tracker, Figma, docs.
Asks you
  • Repo access, stack and commands, rules that must never break, and any existing docs.
→ agents/context-steward.md
// 01 · plan

Planner

Turns an approved spec into a plan of small, ordered tasks that can each be built and tested on their own. It writes no code.

Does
  • Reads the spec from the Product Spec Writer, the repo context, and the Design tokens.
  • Writes plan.md: tasks of 150 lines of code or fewer, each listing the files it touches, its interface, a one-sentence acceptance test and a rollback.
  • Sends unclear specs back to spec review rather than guessing. Ambiguity costs the most when agents are the ones executing it.
Asks you
  • Where specs live, your issue tracker, and whether a plan needs approval before coding starts.
→ agents/planner.md
// 02 · build

Coder

Builds one task at a time: one branch, one PR, one review cycle. Small changes keep both agents and reviewers accurate.

Does
  • Writes code and tests together, test-first where it can, because tests keep the agent from making things up.
  • Runs typecheck, tests and lint locally, then self-checks with the reviewer subagent and a subset of the evals before any person looks.
  • Writes the PR description from the task's plan entry and links the spec. It never pushes to main.
Asks you
  • Branch and PR conventions, test commands, and the areas of the code it must not touch.
→ agents/coder.md
// 03 · ship

Reviewer & Security

Sets a minimum quality bar on every PR, and helps you answer security reviews from enterprise buyers.

Does
  • Runs in CI on every PR. It checks that the PR matches the spec first, because scope creep is the most common agent failure. Then it checks error paths, N+1 queries, injection and SSRF risks, and test coverage of new code paths.
  • Posts inline comments marked with 🤖 so they're easy to filter. It also runs dependency and secret scans.
  • Owns the prompt-injection defenses and audit logging. It also owns an "AI in the SDLC" one-page policy you can hand to a buyer's security team.
Asks you
  • CI provider, security tools, compliance targets (SOC 2, HIPAA, GDPR), and who signs off on merges.
→ agents/reviewer-security.md
// 03 · ship

Release & Oncall

Gets merged code to users safely, and is the first responder when something breaks.

Does
  • Runs migrations and smoke tests in staging, prepares canary releases behind feature flags, watches error-rate targets, and has a rollback plan ready. A person flips every production switch.
  • When an alert fires, queries logs and traces and writes an incident summary within 5 minutes, including the 3 most likely causes and commands to test each.
  • Drafts blameless postmortems and the weekly changelog, which goes to Product's launch agent.
Asks you
  • Hosting and deploy process, environments, feature-flag tool, and monitoring and paging (Sentry, Datadog, PagerDuty).
→ agents/release-oncall.md
// measure & learn

Evals & Flow Metrics

Keeps the system honest about quality. Without evals, every prompt change is a guess.

Does
  • Builds the eval suite: a regression set that starts at 10 real tasks and grows from real failures to 20–50, an AI judge that scores work against a rubric, and a red-team set (prompt injection, malicious diffs, tool misuse). It runs nightly.
  • Recommends agent tracing (Langfuse or Braintrust) and asks you to connect CI and your tracker read-only.
  • Monday scorecard: lead time from spec to merge, share of PRs merged on the first pass, review wait, eval pass rate, escaped defects, and how much of the agents' code humans rewrite.
Asks you
  • CI and tracing tools, where the dashboard should live, and your current quality pain points.
→ agents/evals-metrics.md

Three human gates, no exceptions. Gate 1: a person approves every spec before code is written. Gate 2: a person approves every merge to main. Gate 3: a person flips every production deploy and flag. Agents generate and recommend. People decide.

// always needs your approval

  • Specs and plans before coding starts
  • Every merge to main
  • Production deploys, flag flips and migrations
  • Any access to production data or secrets
  • Infrastructure, permission and CI changes, and new services that touch user data

// red flags to watch

  • PRs wait more than 24h for a person: WIP limits are too loose
  • Agent PRs grow beyond ~150 lines: the Planner isn't breaking work down enough
  • Humans rewrite more and more of the agents' code: specs are getting sloppy or prompts are stale
  • Eval pass rate drops: a prompt or tool has regressed, so investigate the same day
  • Features ship with no keep, iterate or kill verdict: that's motion, not learning
