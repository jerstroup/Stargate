// DATA & ANALYTICS · AGENT SYSTEM

A data team of agents that gives everyone one trusted number

Seven agents that work like a small data team. Two bring data in safely. One defines what every metric means. Two answer questions and build dashboards. One watches data quality around the clock. An orchestrator decides which requests get done first. Every answer shows the query behind it, so anyone can check it. Copy the setup prompt into Claude. It will interview you about your data and then write the whole system as a folder of agent files.

The goal the system works toward

Every agent, every task, and every weekly report is judged against one outcome.

// north star

Every team gets fast, trusted answers: one definition per metric, fresh and tested data, and every number traceable to the query that produced it.

The system doesn't count dashboards built or tables loaded as wins. They only matter when people use the numbers to decide something. This system also feeds the measurement agents in Marketing, Sales, Product and Finance, so the whole company works from the same numbers.

The agents and what each one does

Each agent becomes its own markdown file. The defaults below are best practice. The setup interview adjusts them to your stage, data sources, tools and privacy requirements.

// control

Data Orchestrator

Acts as head of data. Runs one queue for every data request, from people and from the measurement agents in the other systems. It decides what gets built first and keeps an owner on every metric.

Does
  • Prioritizes requests by the decision each one supports, not by who asked loudest. It pushes back on one-off requests that should become a certified metric.
  • Enforces "no metric exists unless it's defined" and keeps a register of who owns each metric.
  • Matches the stack to your stage: spreadsheets first, then a warehouse plus dbt plus a BI tool, then a semantic layer. It tells you when it's time to hire a data lead.
Asks you
  • The 5 questions leadership asks every week, who uses the data, and how much you can spend on tools and warehouse each month.
→ agents/data-orchestrator.md
// 01 · collect

Governance & Access

Makes sure the right people, and only the right agents, can see the right data, and that personal data is minimized and protected.

Does
  • Classifies every source and column: public, internal, confidential or PII. It masks or excludes sensitive fields by default.
  • Designs access roles, including a read-only role for agents and row-level limits on sensitive tables. It handles access requests and keeps an audit trail.
  • Supports privacy obligations (GDPR, CCPA, HIPAA where they apply): retention rules, deletion requests, and a data contract with engineering for schema changes.
Asks you
  • What sensitive data you hold, which rules apply to you, and who can approve access.
→ agents/governance-access.md
// 01 · collect

Ingestion & Pipelines

Gets every important source into one place, reliably and cheaply, without running analytics against your production database.

Does
  • Recommends one warehouse and sticks with it: BigQuery, Snowflake, MotherDuck or Postgres, chosen for your stack and budget.
  • Connects sources (a read replica of the app database, Stripe, CRM, product events, support, ads) using Fivetran, Airbyte or dlt.
  • Keeps a source inventory with each source's freshness target, owner and cost, and partitions large tables by date to keep queries cheap.
Asks you
  • Where your data lives today, which source is the truth for each subject, and how often each needs to update.
→ agents/ingestion-pipelines.md
// 02 · model

Modeling & Semantic Layer

Turns raw tables into clean models and a single metric dictionary, so agents and people know exactly what "active user" or "ARR" means.

Does
  • Builds dbt models in layers: staging → intermediate → marts, with documentation on every model.
  • Writes metrics.yml. Every metric has a definition, grain, owner, filters and approved SQL (see the example semantic layer).
  • Allows one definition per metric, shared with Finance, and runs reconciliation checks (e.g. the movements in ARR must add up to net new ARR).
Asks you
  • Your key metrics and how you currently define them, any numbers people disagree about, and who owns each metric.
→ agents/modeling-semantic.md
// 03 · serve

Analyst Agent

Answers any teammate's question in plain English, and always shows its work.

Does
  • Works from the semantic layer, model docs and a library of verified example queries. Uses certified metrics before writing new SQL.
  • For each question it proposes the SQL, runs it on a sample, shows the SQL, the metric definition and the result, and then runs the full query.
  • Never states a number without its query. It says so when a question can't be answered from certified data, and passes recurring questions to Dashboards.
Asks you
  • Where people ask questions (Slack, chat, a Claude Project) and any queries you already trust.
→ agents/analyst.md
// 03 · serve

Dashboards & Insights

Gives each role a small, honest dashboard and a weekly summary of what changed and why.

Does
  • Builds one dashboard per role: founder KPIs, marketing, sales, product, finance and support. It uses Metabase, Lightdash or Looker Studio.
  • Every chart traces back to a named metric, so there are no duplicate definitions. It retires dashboards nobody opens.
  • Writes a weekly digest of what moved, which segments drove it and what it's correlated with, and runs feature-adoption reports for product launches.
Asks you
  • Your BI tool, who needs which view, and your reporting rhythm (weekly team review, monthly board update).
→ agents/dashboards-insights.md
// measure & learn

Data Quality & Observability

Protects trust in the numbers. It treats bad data and schema changes as incidents, not surprises.

Does
  • Runs dbt tests on every model: not-null and unique keys, accepted values, relationships between tables. It also checks each source against its freshness target.
  • Detects anomalies nightly by comparing each metric with its 14-day average (alerting on swings beyond 3 standard deviations), and tries to explain them: which segment moved, recent deploys, changes in ticket volume.
  • When a check fails, it opens a ticket with the suspected upstream cause. It sends a weekly trust scorecard covering tests, freshness, usage and warehouse cost.
Asks you
  • Where alerts should go, your issue tracker, and your freshness requirements for critical metrics.
→ agents/data-quality.md

Agents get a read-only role, always. Never connect an agent to your production database or give it write access to the warehouse. Agents propose changes to schemas, models and access as reviewed pull requests or requests to you. They never run destructive SQL themselves.

// always needs your approval

  • Granting or changing anyone's data access
  • Any write, schema change or destructive SQL (DROP, DELETE, UPDATE)
  • New or changed metric definitions
  • Adding sources that contain personal data, or sharing data externally
  • Syncing data back into CRM or other tools, and warehouse spend above budget

// red flags to watch

  • Two teams report different numbers for the same metric: the dictionary is being bypassed
  • An answer without its SQL: the analyst can't be verified
  • Tests failing quietly or data going stale: alerts aren't reaching an owner
  • Dashboards nobody opens: you built for completeness instead of decisions
  • Warehouse cost spikes: missing partitions or runaway queries
